# 클로드 goal 기능

Claude Code에는 세션을 여러 턴에 걸쳐 계속 작동시키는 방법이 두 가지 있다. 표로 정리하면 이렇다.

| | `/loop` | `/goal` |
|---|---|---|
| 기준 | **시간** — 정해진 간격마다 다시 실행 | **조건** — 완료 조건이 충족될 때까지 반복 |
| 비유 | 크론 잡: "N분마다 이 프롬프트를 실행해라" | "이 문제가 해결될 때까지 멈추지 마라" |
| 다음 턴 시작 시점 | 시간 간격이 경과할 때 | 이전 턴이 끝날 때마다 즉시 |
| 멈추는 시점 | 사용자가 중지하거나 Claude가 작업 완료로 판단할 때 | 평가자(작은 모델, 기본 Haiku)가 조건 충족을 확인할 때 |
| 판단 주체 | 작업을 수행하는 Claude 자신 | 매 턴 후 별도로 붙는 평가 모델 |

즉 `/loop`는 "얼마나 자주 다시 볼지"를, `/goal`은 "언제 멈출지"를 결정한다. 이 둘을 합치면(`/loop 1m /goal ...`), 평소엔 주기적으로 확인만 하다가 할 일이 생기면 그때부터 끝날 때까지 자율적으로 파고드는 패턴을 만들 수 있다.

## 케이스 1 — `/goal` 단독

`goal-case/fizzbuzz.py`에 일부러 버그를 심어뒀다 (3과 5 공배수일 때 "FizzBuzz"가 아니라 "Fizz"만 반환). `goal-case/test_fizzbuzz.py`를 돌리면 1개 실패한다.

```
/goal 이 폴더의 pytest 테스트가 모두 통과할 때까지
```

**결과**: 몇 턴 만에 원인(3의 배수 분기가 15의 배수 케이스보다 먼저 걸림)을 찾아 `if i % 15 == 0` 분기를 맨 앞에 추가해서 고쳤고, pytest 3개 모두 통과했다. 별도로 "테스트 돌려봐"라고 시키지 않아도, 조건이 "pytest 통과"였기 때문에 스스로 테스트를 실행하고 결과를 확인하는 과정을 반복했다.

## 케이스 2 — `/loop` + `/goal` 결합

`loop-goal-case/tasks.md`에 할 일 목록을 적어두고, 아래 명령으로 1분마다 확인하면서 할 일이 있으면 끝날 때까지 자율적으로 처리하고 없으면 대기하는 패턴을 테스트했다.

```
/loop 1m /goal tasks.md에 있는 미완료 항목(- [ ])을 모두 처리하고, 처리한 항목은 - [x]로 체크해줘
```

**결과**: 첫 틱에서 바로 `- [ ] hello.py 파일을 만들고, 실행하면 "안녕, playground!"를 출력하게 한다` 항목을 발견해 `hello.py`를 생성하고, `tasks.md`의 체크박스를 `- [x]`로 바꿔놓았다. 이후에는 처리할 항목이 없어 다음 틱마다 조용히 대기만 했다.

## 배운 점

- `/goal`은 독립적으로 명령을 실행하거나 파일을 읽지 않는다 — 평가자는 오직 **대화에 이미 나타난 내용**만 보고 판단한다. 그래서 조건은 "Claude가 스스로 증명할 수 있는 것"으로 써야 한다 (예: 테스트 실행 결과가 대화 기록에 남는 것).
- `/goal`은 권한 모드를 바꾸지 않는다. 기본 모드에서는 도구 호출마다 여전히 승인이 필요했고, 완전 무인 실행을 보려면 자동 모드(auto mode)와 같이 써야 한다 — 그만큼 위험도 커지므로 처음엔 기본 모드로 지켜보는 게 안전했다.
- `/loop`와 `/goal`을 결합하면 "평소엔 대기하다가, 할 일이 주어지면 그때부터 끝까지 파고드는" 자율 루프를 만들 수 있다. 세션(터미널)이 열려 있는 동안만 작동하고, 반복 작업은 7일 후 자동 만료된다.
